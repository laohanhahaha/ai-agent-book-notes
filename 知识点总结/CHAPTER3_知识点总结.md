# Chapter 3 知识点总结：用户记忆和知识库

> 依据：[第三章正文](../book/chapter3.md)、[配套项目目录](README.md)、[实验验收台账](EXPERIMENT_LEDGER.md)，并结合记忆管理、检索融合、上下文分块和 Agent 主循环代码整理。整理日期：2026-09-14。本笔记区分原理、教学实现与实验观察；没有在本次整理中重新运行模型或 API 实验。

## 1. 本章与前两章的关系

- 第一章：Agent 如何通过“模型决策 → 工具行动 → 观察结果”循环完成任务。
- 第二章：一次任务中，怎样组织、缓存、维护和压缩模型上下文。
- 第三章：跨越会话之后，哪些信息应长期保留，怎样组织外部知识，又怎样在需要时把它们送回上下文。

可以把第三章的主线概括为：

```text
对话、文档、业务记录
        ↓ 抽取、整理、保存
用户记忆 / 知识库
        ↓ 索引、检索、按需读取
当前模型上下文
        ↓ 推理与工具调用
回答或行动
        ↓ 经过验证的新事实、反馈
更新记忆与知识库
```

**存进数据库不等于模型已经知道。** 信息还需要经过检索、加载或工具调用，进入当前上下文才能被使用。这种外部记忆更新通常不改变模型参数。

## 2. 用户记忆与知识库有什么区别

| 对比项 | 用户记忆 | 知识库 |
|---|---|---|
| 主要对象 | 某个用户的事实、偏好、经历和关系 | 产品、业务、领域及组织的知识 |
| 主要用途 | 跨会话连续性、个性化和主动关联 | 基于外部证据回答问题、支持业务执行 |
| 常见来源 | 历史对话、经授权的用户资料 | 文档、手册、业务记录、数据集 |
| 更新重点 | 主体归属、时间变化、偏好与事实冲突 | 版本、来源、适用范围和索引同步 |
| 权限边界 | 用户与租户隔离 | 按文档、部门、角色等实施访问控制 |

两者不是互斥技术：用户历史也能做 RAG，知识库也能使用结构化卡片。“知识共享”不代表所有用户都能访问全部内容。

## 3. 记忆写入：不是把聊天记录再复制一份

记忆抽取有三个重点：

1. **选择性**：保留未来有用的信息，过滤寒暄、重复和短暂噪声。
2. **抽象化**：从具体表达中提炼可复用的事实或偏好。
3. **结构化**：明确是谁、何时、发生了什么、在什么条件下成立。

例如，用户说：“我下个月可能搬到杭州，还没决定。”

- 可以记录：用户正在考虑下个月搬到杭州，尚未确定。
- 不能记录：用户现居杭州。

同样要区分“用户说过”“助手建议过”“工具证实了”“已经执行成功”。把建议或计划误写成事实，会让错误在后续会话中持续传播。

有用的记忆字段包括：主体 ID、事实内容、来源会话、记录时间、生效时间、状态和适用条件。这些是工程设计建议，不是所有框架都固定使用的字段。

## 4. 如何评估记忆能力

### 4.1 三层评估框架

书中归纳了三个层次，不应误认为所有公开基准都使用同一分类：

| 层次 | 检查什么 | 示例 |
|---|---|---|
| 基础回忆 | 能否记住并准确复述事实 | 用户偏好哪种回答风格？ |
| 多会话理解与检索 | 能否跨记录关联、消歧、处理更新 | 用户以前住甲地，后来搬家，现在住哪里？ |
| 主动关联服务 | 能否在新任务中发现相关的旧信息 | 安排行程时，主动考虑已确认的时间与偏好 |

需要覆盖的能力包括：个人信息、偏好、话题切换、事实更新、连续性、联合推理、时间理解与冲突处理。

**答对事实与提供恰当的主动服务是不同能力。** 能搜到旧记录，不代表能在用户没明确提醒时想到它；主动建议也不等于获得了下单、付款等执行授权。

### 4.2 本地实验的评估边界

实验 3-1/3-2 使用三层、每层 20 个案例，共 60 个 YAML 案例。验收要求包括：

- 按会话逐次更新记忆；后续生成只能继承记忆状态，不能偷偷保留之前的原始历史；
- 在新问题上测试能否正确使用记忆；
- 使用独立评判调用，并保存回答、记忆产物、请求证据；
- 比较格式时控制案例、生成模型、回答模型与评判标准，记录 token 和延迟。

这与实验 3-9 中“允许检索原始历史”的设置不同。比较时必须先说明系统能访问哪些信息。

## 5. 三个不同维度：放哪里、怎么存、存什么

### 5.1 信息层次：放在哪里

- **原始轨迹**：对话、工具调用、原始证据，用于回溯。
- **长期记忆**：从轨迹中提炼出的可复用事实、偏好和经验。
- **业务状态**：订单是否完成、任务处于哪一步等，由业务系统或确定性程序维护。

三者不能互相冒充。订单系统显示“未付款”，不能因为对话里说“准备付款”就改成“已付款”。

原始事件日志可以采用追加式设计，但不等于无限期保存所有隐私数据。运行时上下文可以压缩重组，长期存储则还要遵守保留、删除和权限政策。

### 5.2 存储格式：怎样表达

这是下一节的 Notes、JSON Cards 等选择，与使用文件还是数据库不是同一问题。

### 5.3 认知分类：存的是什么

| 类型 | 含义 | Agent 中的例子 |
|---|---|---|
| 情景记忆 | 具体经历与发生背景 | 某次会话讨论了一个旅行计划 |
| 语义记忆 | 抽象事实与知识 | 用户偏好简洁的中文解释 |
| 程序性记忆 | 如何完成任务的方法 | 排错流程、操作 SOP、Skill |
| 工作记忆 | 当前任务中可用的信息 | 当前上下文中的问题、状态与证据 |

这是认知科学启发的工程类比，不表示软件实现了人脑的同等机制。

## 6. 四种用户记忆格式

| 格式 | 组织方式 | 优点 | 常见代价 |
|---|---|---|---|
| Simple Notes | 一条条原子事实 | 简洁、易增删 | 容易丢失背景与关系 |
| Enhanced Notes | 带背景的完整段落 | 保留原因、条件和时间线 | 较冗长、可能重复 |
| JSON Cards | 按主题组织层级字段 | 便于定位、校验与程序读取 | schema 维护和字段归属较复杂 |
| Advanced JSON Cards | 卡片中增加背景、人物、关系、时间等 | 更适合消歧和复杂关联 | 抽取、更新与上下文成本更高 |

概念示例，非项目固定 schema：

```json
{
  "subject_id": "user_001",
  "topic": "communication_preference",
  "fact": "学习新概念时希望结合代码解释",
  "source_session": "session_12",
  "status": "confirmed"
}
```

复杂格式不是自动更准确：信息抽错了，JSON 再规整也只是结构化的错误。简单记忆的某次按键访问可能很快，也不能据此声称整个抽取、搜索和更新系统都是 O(1)。

本地阅读入口：[memory_manager.py](user-memory/memory_manager.py)。它把不同格式放在统一管理接口后面，提供增删改、上下文生成和搜索等操作。

## 7. 对话与后台记忆处理分离

`user-memory` 项目把即时交互与记忆整理拆开：

```text
Conversational Agent：读取记忆、与用户交互
Background Memory Processor：分析新对话、提出并应用记忆更新
Memory Manager：维护不同格式的记忆、保存与加载
```

对应代码：

- [conversational_agent.py](user-memory/conversational_agent.py)：面向用户的对话。
- [background_memory_processor.py](user-memory/background_memory_processor.py)：批量或后台处理新对话。
- [memory_manager.py](user-memory/memory_manager.py)：存储与访问接口。

这样可以把昂贵的整理步骤移出即时回答路径，但会出现更新延迟。需要考虑重复处理、并发写入、失败重试与“后台尚未处理但当前会话已知”的情况。

## 8. User as Code：把部分记忆变成可计算的数据与规则

书中讨论了一种进一步的表示方式：

```text
事实日志 → 类型化对象与规则 → 程序计算 / 一致性检查 → 模型解释
```

例如，把多个事件的日期保存为规范字段，用程序计算间隔，而不是每次让模型从长历史中重新数日期。

适用点是确定性计算、状态检查、约束判断。自然语言模型负责理解与解释，代码承担明确的计算。

边界要记住：

- 程序算得正确，不保证抽取进来的事实正确。
- 业务规则需要明确来源与版本，不能让模型凭空制定。
- LLM 生成的代码需要校验和受限执行，不能因为它叫“记忆”就直接运行。
- 不是所有经历和偏好都值得转成代码；保留原文和语义背景仍有价值。

## 9. 记忆框架案例与更新路线

本章通过 mem0、Memobase 等案例讨论工程取舍，而不是要求所有系统采用某个框架。

- **写入时整理**：面对新事实，选择新增、更新、删除或不操作，维护较精炼的当前记忆。
- **追加事实、读取时消歧**：保留变化历史，在查询时根据时间、主体和状态判断哪些仍有效。
- **画像 + 事件 + 缓冲区**：把稳定画像与具体经历分开，积累一定对话后再批量整理。

第一种把成本放在写入端；第二种保留更多证据，但把复杂性转移到检索与解释端；第三种要管理批处理的延迟。

书中的版本案例和本地教学实现不能直接代表框架的所有版本。配套入口：[mem0](mem0/README.md)、[memobase](memobase/README.md)。

## 10. 记忆压缩、整理与遗忘

长期记忆也会膨胀，需要周期性维护：

1. 根据重要性、时间、访问情况与独特性筛选候选。
2. 聚合相近记录、去重、形成摘要。
3. 从多次事件中提炼稳定模式，同时保留例外和来源。
4. 标记过期状态、处理冲突，并保留必要的变更历史。

**低频不等于无价值，最新也不一定最可信。** 冲突可能来自不同主体、不同时间、误述或未完成计划，应先定位原因，再决定更新、并存还是向用户确认。

与第二章的区别：上下文压缩管理“本次模型看到什么”；记忆整理管理“未来会话还能找回什么”。二者都可能有损，但作用范围不同。

## 11. 隐私保护：日志脱敏

日志可能包含 API Key、认证头、邮箱、电话和其他个人信息。实验 3-3 比较：

- **正则规则**：适合格式明确的敏感信息，快速、可解释。
- **本地模型识别**：补充自然语言或非固定格式的敏感内容识别。
- **混合方式**：结合规则覆盖与语义识别，但仍需测量漏报、误报。

评估不仅看“替换了多少内容”，还要看：位置级 precision/recall、残余泄露、脱敏后的任务可用性与延迟。

本地运行减少某些外传路径，却不自动解决日志访问控制、磁盘保留和备份泄露。脱敏也不等于匿名化；应从一开始就减少收集不必要的敏感信息。

## 12. RAG：检索增强生成

RAG（Retrieval-Augmented Generation）不是一种“把资料训练进模型”的操作，而是在回答时补充外部证据。

### 离线或索引阶段

```text
获取文档 → 清洗 → 分块 → 保存来源与元数据
                        → 生成向量 / 建立倒排索引
```

### 在线回答阶段

```text
用户问题 → 检索相关片段 → 融合与重排 → 组织证据上下文
                                      → 模型回答并引用来源
```

权限和有效期检查应贯穿检索与证据读取，确保无权访问或已失效的内容不会流入模型上下文。证据不足时，应明确缺失，必要时补查，而不是补造答案。

检索系统回答“哪些资料可能相关”；生成模型回答“这些资料如何支持用户的问题”。相关性不等于真实性，检索命中也不等于答案一定正确。

## 13. 文档分块：召回的基本单位

| 方法 | 思路 | 取舍 |
|---|---|---|
| 固定大小 + 重叠 | 按长度切分，相邻块保留部分重复 | 简单，但可能切断条件与引用 |
| 结构化 / 递归分块 | 尽量按标题、段落、句子切分 | 保留结构，但块长度不均 |
| 语义分块 | 根据主题变化划分 | 语义连贯，但建库更复杂 |

块太小，缺少背景；块太大，主题混杂、召回不精确且占上下文。书中的长度与重叠比例可作实验起点，不是普适最优值。

每块应保留文档 ID、标题路径、位置、来源和版本。不要只存一段失去出处的文本。

## 14. 稠密嵌入：用向量表达语义

Embedding 模型把文本映射为定长向量，让语义相近的内容有机会在向量空间中接近。查询与文档应采用兼容的模型、编码方式和距离度量。

常用余弦相似度：

```text
cos(q, d) = dot(q, d) / (norm(q) × norm(d))
```

它比较方向，理论范围为 [-1, 1]；实际分数分布取决于模型和数据。向量模长不是文本长度，语义无关的向量也不保证余弦恰好接近 0。

### 从词向量到上下文表示

- Word2Vec 等静态词向量：同一个词通常对应同一表示，多义词受限。
- 上下文感知编码器：结合周围文本表示词义。
- 检索专用嵌入模型：进一步通过适合检索的目标学习查询与文本的匹配。

“使用了 BERT”不自动等于“得到了优质句向量”；池化方式和训练目标同样重要。BGE-M3 等模型还体现了同一模型提供多种检索表示的思路。

### 精确搜索与 ANN

- 精确搜索：与全部候选比较，可作为对照真值。
- ANN：近似最近邻搜索，用一定召回损失换取效率。
- ANNOY：树结构索引，适合构建后主要读取的场景。
- HNSW：分层图索引，可在相应实现中支持增量插入。

不能只背“谁更快”：要固定向量、查询和硬件，再比较召回率、建库时间、查询延迟、内存与更新行为。

## 15. 稀疏检索：TF-IDF、BM25 与倒排索引

**倒排索引**把“文档中有哪些词”反过来组织成“这个词出现在哪些文档中”，不必每次扫描全部文档。

- TF：某词在文档里出现多少次。
- IDF：某词在整个语料中越少见，通常越有区分力。
- TF-IDF：结合词频与区分力。
- BM25：进一步使用词频饱和与文档长度归一化。

BM25 的基本评分结构可写成：

```text
score(q, d) = 对查询词 t 求和：
  IDF(t) × tf(t,d) × (k1 + 1)
  / [tf(t,d) + k1 × (1 - b + b × len(d)/avg_len)]
```

`k1` 控制词频饱和，`b` 控制文档长度归一化；分词、停用词和 IDF 具体形式也会影响结果。

BM25 适合专有名词、编号、错误码等精确匹配，但词袋表示难以表达词序关系，对纯同义改写也可能漏检。这里说的是传统词项检索；SPLADE 等学习型稀疏表示可以进行语义扩展，不能把所有稀疏检索都说成“不懂语义”。

代码入口：[bm25_engine.py](sparse-embedding/bm25_engine.py)。

## 16. 混合检索与重排序

```text
              ┌─ 稠密召回：语义接近 ─┐
用户问题 ─────┤                      ├─ 融合去重 → 重排序 → 证据片段
              └─ 稀疏召回：词项匹配 ─┘
```

两种常见融合方法：

1. **分数归一化后加权**：把不同尺度的分数转换后组合；权重需要评估。
2. **RRF（倒数排名融合）**：不直接比较原始分数，而是累计不同列表的排名贡献。

```text
RRF_score(d) = Σ 1 / (c + rank(d))
```

这里 `c` 是平滑常数，不是返回条数 top-k；本地 [fusion.py](retrieval-pipeline/fusion.py) 实现了 RRF 和 min-max 归一化加权融合。

重排序器通常把查询和候选文档一起输入 Cross-Encoder，精细评估相关性。它比单向量相似度计算更贵，因此常只处理召回出的有限候选。

**重排只能重新排列已有候选，救不了没有被召回的证据。** 混合检索和重排也不是每个小型知识库都必须配置，应通过消融实验判断收益。

## 17. 检索与回答应该怎样评估

| 指标 | 回答的问题 |
|---|---|
| Recall@k | 所有标注相关文档中，有多少比例出现在前 k 项？ |
| Hit@k | 前 k 项是否至少命中一篇相关文档？ |
| MRR | 第一篇相关文档平均排得多靠前？ |
| nDCG@k | 考虑相关性等级与位置后，排序质量如何？ |
| 延迟与成本 | 建库、检索、重排、生成分别花多少时间与资源？ |
| 答案与引用质量 | 回答是否正确，引用是否真正支持对应结论？ |

例如，一个问题共有 4 篇相关文档，前 5 项找到了 2 篇：Recall@5 = 2/4 = 0.5，Hit@5 = 1。只有每个查询恰有一篇相关文档时，两者才会在该设置下相同。

比较不同方案时固定语料、问题、标注和生成条件，分开统计简单题、多跳题、精确名称题等。还要测试无答案、过期知识、矛盾证据和跨用户越权等情况。

## 18. 为什么不能只靠扁平文本的 Top-k

扁平分块检索擅长找局部证据，但有三个局限：

- 片段之间的实体关系与适用条件可能断裂。
- 全局概览可能散落在大量片段中。
- 找到少量相关案例，不等于掌握总体分布。

例如，“找几个退款案例”可以做检索；“统计过去一年所有退款的成功率”需要有覆盖范围的完整数据与程序聚合，不能对 Top-k 案例直接算总体成功率。

同样，几个成功或失败案例只能提供线索，不能自动推导出“只有满足某条件才能成功”这样的排他规则。提炼规则还需要检查反例、遗漏条件和样本偏差。

## 19. 结构化索引：RAPTOR 与 GraphRAG

| 方案 | 核心结构 | 更适合解决的问题 | 主要代价 |
|---|---|---|---|
| 扁平分块 | 一组可搜索片段 | 局部、直接的事实查询 | 跨块关联与全局覆盖不足 |
| RAPTOR | 片段聚类后递归生成摘要层级 | 兼顾主题概览与细节 | 摘要成本、压缩损失和更新传播 |
| GraphRAG | 实体、关系、社区与摘要 | 关系查询、多跳关联和全局主题 | 抽取、消歧、图维护与建库成本 |

RAPTOR 的基本流程：分块 → 嵌入 → 聚类 → 总结为父节点 → 继续构建更高层。查询可以跨层检索，不一定只能从根节点一路向下。

GraphRAG 的基本流程：抽取实体和关系 → 构图 → 社区发现与摘要 → 按局部关系或全局主题检索。图结构本身不会自动解决同名人物、实体别名或错误关系，需要额外消歧与证据检查。

简单的“主体—关系—客体”三元组可能丢失时间、条件和否定，应关联原始证据及必要元数据。

这三种方案不是必须逐级升级的路线，而是不同查询需求下的取舍。代码入口：[raptor_indexer.py](structured-index/raptor_indexer.py)、[graphrag_indexer.py](structured-index/graphrag_indexer.py)。

## 20. 文件系统范式：让知识可浏览、可按层读取

本章借助 OpenViking 等案例介绍另一种组织思路：用 URI、目录层级、摘要与链接，让 Agent 能先理解知识分布，再按需深入。

- L0：极短摘要，用于判断是否值得读取。
- L1：概览，说明主题结构与主要内容。
- L2：详细原文或完整材料。
- 纵向目录摘要提供层级，横向链接连接相关主题，入口索引帮助发现可用知识。

核心不是“把数据库换成磁盘文件”，而是提供可导航的信息结构。URI 可以由不同存储后端实现，文件式组织也可以与向量检索、数据库并存。

摘要是导航，不是事实全集；需要精确结论时仍应下钻原文。

## 21. 知识更新：增量维护与定期整理

### 21.1 区分三层产物

```text
原始证据层：对话、文档、业务记录
知识层：整理后的事实、规则、主题文档
派生索引层：向量、倒排索引、摘要树、关系图
```

更新文档但不更新索引，会继续搜出旧内容；只改派生摘要而不保存来源，会失去追溯能力。

### 21.2 增量更新

发现新证据 → 提议修改与来源 → 审核适用条件、冲突与遗漏 → 验证 → 发布 → 更新受影响的索引。

书中提出了提议 Agent 与审核 Agent 分工、用 diff/PR 保留修改记录的方案。重点是证据审查、版本可追踪和可回滚，不是要求所有记忆系统都使用 Git 或两个 Agent。

审核者应能读取授权范围内的相关原始资料，而不只看到提议者精选的证据。高影响规则需要相应负责人确认；自动重试也应有成本与次数上限。

### 21.3 定期整理

增量更新解决“刚出现的新变化”，定期整理解决长期积累的重复、矛盾、过期和结构失衡。应回看原始资料、补齐遗漏条件、重组知识，并用代表性查询做回归测试。

## 22. Agentic RAG：把检索交给 ReAct 循环调度

普通的一次检索 RAG：预设检索步骤 → 一次取得证据 → 生成回答。

Agentic RAG：模型根据缺失信息自行决定查询、读文档、修改查询与继续补查。

```text
问题 → 模型提出检索调用 → 程序查询知识库
               ↑                ↓
          信息仍不足 ← 工具结果加入上下文
                                ↓ 信息足够
                              最终回答
```

它延续了第一章的流程，只是把网页搜索换成了知识库搜索、读取完整文档等工具。

本地 [agent.py](agentic-rag/agent.py) 中，`query()` 承担 Agent 主循环，`query_non_agentic()` 提供非 Agentic 对照；[tools.py](agentic-rag/tools.py) 定义 `knowledge_base_search()` 和 `get_document()` 等访问能力。

适合拆解、多跳与证据冲突问题，但通常增加模型调用次数、检索次数和延迟。简单问题可能一次检索就够；如果知识根本没入库、查询缺乏线索或索引始终漏检，增加循环次数也不保证解决。

## 23. 用 Agentic RAG 检索用户历史

实验 3-9 把历史对话分块、索引，并提供 `search_user_memory` 工具。模型可以先搜一个主题，发现缺少信息后再补查人物、日期或相关事件。

这里必须分清：

- 长期历史存储：可供检索的原始资料。
- 本次模型上下文：当前问题、工具调用与实际返回的片段。

**每次检索返回的内容会进入本次上下文，但并不代表全部历史一次性进入上下文。** 为避免“我”“他”“上个月”失去含义，应保存说话人、会话时间、实体与来源关系。

## 24. Contextual Retrieval：先补背景，再建立索引

普通分块可能只留下“它比上一代提升了 20%”，却丢失“它是谁、哪一代、什么指标”。

Contextual Retrieval 在索引阶段，让模型结合完整来源文档和目标片段，生成一段短背景，再与原片段拼接：

```text
完整文档 + 目标 chunk
          ↓ 生成局部背景
背景前缀 + 原始 chunk
          ↓
稠密索引 / BM25 索引
```

区别在于：它不是回答时临时总结，也不是只保留摘要；目标是让片段在被检索前就更容易定位、理解。

本地 [contextual_chunking.py](contextual-retrieval/contextual_chunking.py) 分别保存原文 `text`、背景 `context`、拼接内容 `contextualized_text` 和元数据，便于对照与追溯。

成本发生在建库与更新阶段：需要模型生成背景，并同步处理文档版本变化。背景也可能产生幻觉，应验证其是否得到原文支持。

原文和 README 引述的失败率降幅来自特定外部实验，不等于本地项目已经复现。需要用同一语料与查询，对 plain/contextual 的稀疏、稠密或混合检索进行控制实验。

## 25. 双层用户记忆：概览负责发现，检索负责补证

只做按需检索有一个问题：模型如果没想到某段经历相关，可能根本不会搜它。

双层结构把两种能力组合起来：

- **概览层**：少量结构化记忆卡片，让模型知道用户有哪些重要背景。
- **细节层**：通过 RAG 回查原始历史，验证具体日期、条件和变化过程。

概览帮助“想起可能有关的事情”，细节检索帮助“确认到底发生过什么”。实验 3-11 将 Advanced JSON Cards 与上下文感知检索结合，并与 plain、contextual 方案对照。

卡片也需要更新、权限控制与上下文预算；不能把所有用户记录永久塞进 system prompt。与第二章衔接时，应按稳定性设计卡片的加载位置，避免为缓存保留已经过期的事实。

## 26. 从数据集中提炼深层知识

这一节从“检索已有文字”走向“从大量案例中提炼可解释结构”。可以分成四步理解：

1. **自下而上发现因子**：从样本中发现需要记录哪些字段，去重归一，形成通用字段与主题扩展。
2. **结构化抽取**：按 schema 提取各案例的信息；未提及的事实保留未知状态，不随意填成否定。
3. **聚类与原型统计**：规范化数值、编码类别，聚合相似案例，提取原型及区分性因子。
4. **交互应用**：询问缺失的重要信息，匹配原型，由模型解释有证据支持的统计结果。

本地对应：[discovery.py](structured-knowledge-extraction/discovery.py)、[extractor.py](structured-knowledge-extraction/extractor.py)、[archetypes.py](structured-knowledge-extraction/archetypes.py)、[advisor_agent.py](structured-knowledge-extraction/advisor_agent.py)。正文可以按“离线提炼 / 在线使用”两大阶段理解，项目再把它们拆为具体步骤。

需要避免三个误解：

- 因子能区分聚类，不代表它是结果变化的因果原因。
- 样本中的典型范围，不代表对新个体的确定预测。
- 模型解释得流畅，不代表数据抽取和统计一定可靠。

训练与留出测试必须分开，因子发现与原型构建不能偷看留出答案。本章司法案例是技术实验；原型统计不能替代现行规则核验或专业判断。

## 27. 多模态记忆的三条路线

- 保存图片、音频等原件，生成文字描述帮助检索，必要时读取原件。
- 使用多模态嵌入，让文本查询与图像、音频等内容进行匹配。
- 在专门模型中研究潜在表示或参数层面的记忆。

文字描述可能漏掉视觉细节，所以不能一概删掉原件。向量是检索表示，也不是普通聊天 API 可以直接理解的“一个记忆 token”。

书中对压缩表示的设想应按专用模型机制理解：把一串 embedding 数字写进 JSON，通常只会消耗文本 token，不会自动获得“一张脸只占一个 token”的能力。

## 29. 为后续提炼 Skill 保留的候选

先完成知识整理，再把内容转换成任务流程。每一节都保留来源，但不要求每一节都单独创建 Skill。

| 知识范围 | 可提炼的任务 | 更合适的承载方式 |
|---|---|---|
| 记忆抽取、格式、冲突和整理 | 设计或审查长期记忆系统 | 一个工作流 Skill + schema 示例 |
| 三层评估、实验控制 | 建立记忆评测与失败分析 | 评估 Skill + 案例和评分资源 |
| 脱敏 | 检查日志泄露并验证脱敏效果 | 独立流程 + 规则与测试脚本 |
| 分块、嵌入、BM25、融合、重排 | 设计、调优和诊断 RAG | 工作流 Skill；算法细节作为参考 |
| RAPTOR、GraphRAG、文件层级 | 按查询需求选择知识组织方案 | 决策参考，可并入 RAG Skill |
| 增量更新、整理、回归 | 审查并发布知识库更新 | 更新工作流 + 检查清单 |
| Agentic、Contextual、双层记忆 | 诊断检索不足并组合改进方案 | 扩展流程与对照实验模板 |
| 因子抽取、原型统计 | 从案例提炼可解释结构 | 独立数据处理流程 + 验证脚本 |
| 认知类比、User as Code、多模态 | 理解表示选择与适用边界 | 参考资料；成熟任务再提炼流程 |

真正的 Skill 需要定义：何时使用、输入、执行步骤、分支条件、输出、验证方法和失败处理。知识总结解释“是什么与为什么”，Skill 则要指导“遇到什么任务应怎样做，怎样证明做对了”。本次只整理候选，不创建或安装 Skill。

## 30. 学完本章后应能回答的问题

> 参考答案补充于 2026-09-15。“原文依据”为短摘录，答案为归纳；超出原文直接论断的工程或方法论判断单独标注。来源链接定位到本次核对的原文行号。

### 30.1 为什么保存全部聊天记录不等于拥有好用的长期记忆？

**参考答案：** 完整记录提供原始证据，但还需要选择、提炼、组织和检索，才能在新任务中及时找到有用信息。否则，事实散落在大量对话里，重复、过期和冲突难以处理。好用的长期记忆应保留稳定事实、来源和生效条件，并在需要时载入当前上下文，而不是每次把全部记录交给模型。

**原文依据：** “记忆并非简单记录用户说过的每一句话。”见[第三章·用户记忆系统](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L17)。选择、抽象与结构化见[第 43 行起](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L43)。

### 30.2 用户记忆、当前上下文和业务状态分别由谁维护？

**参考答案：** 用户记忆由持久存储与记忆处理模块维护，模型可通过受控工具提出读取或更新；当前上下文由 Harness 按本次任务组装，包含规则、问题、历史和检索结果；业务状态由应用逻辑及业务系统维护，工具执行结果推动其更新。三者应关联但职责不同，例如用户说“打算付款”不能直接将订单状态改为“已付款”。

**原文依据：** “Agent 通过特定工具调用显式读取和更新长期记忆”。见[第三章·记忆层次](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L90)，运行时上下文与业务状态分别见[第 86 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L86)和[第 92 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L92)。职责分工是结合这三层概念的工程归纳。

### 30.3 怎样避免把计划、助手建议或他人经历记成用户事实？

**参考答案：** 抽取时保留说话人、事实主体、来源、时间和状态，区分已确认、计划、假设与建议。遇到“可能搬家”应记录为未确定计划；助手提议只说明曾给出建议；用户转述家人经历应绑定家人的实体。更新冲突时先核查同一主体和生效时间，重要且不明确的信息再向用户确认。

**原文依据：** “询问贷款状态时需分辨正在履行的有效合同，忽略过去咨询但未生效的报价。”见[第三章·多会话检索](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L70)。来源、主体、关系和时间字段见[Advanced JSON Cards](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L109)。具体的计划/建议区分是据此归纳的抽取规则。

### 30.4 四种记忆格式分别在哪些任务上有优势与代价？

**参考答案：** Simple Notes 适合少量独立事实，生成和访问简单，但关系容易碎片化；Enhanced Notes 适合保留事件背景和条件，代价是冗余与更新复杂；JSON Cards 适合分类清晰、需要字段读取与局部更新的信息，但难表达跨类别内容；Advanced JSON Cards 适合多人物、关系和时间消歧，维护与上下文成本更高。可按信息类型混用。

**原文依据：** “保留信息的叙事结构确保语义完整性和丰富性。”见[第三章·Enhanced Notes](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L105)。其余格式与选型见[四种存储格式](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L103)及[混合使用标准](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L113)。

### 30.5 为什么跨会话评估要控制是否能访问原始历史？

**参考答案：** 允许读取原始历史时，即使持久记忆漏掉信息，系统也可能重新检索答对；禁止读取时，才更直接检验记忆抽取、更新和保留是否充分。两种设置测量的能力不同，应分别报告。实验 3-1/3-2 限制后续只继承记忆状态，实验 3-9 则把完整历史作为可检索知识库，比较成绩时必须说明这一差异。

**原文依据：** “在仅能访问记忆、不可回看之前会话原始对话的前提下”。见[第三章·实验 3-1](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L76)。允许历史检索的另一设置见[实验 3-9](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L611)。

### 30.6 BM25 与稠密检索为什么互补，重排为什么救不了漏召回？

**参考答案：** BM25 利用词项匹配，适合名称、编号和错误码；稠密检索利用语义表示，适合同义改写和概念关联。将两路候选融合可以补充各自遗漏。重排器只对候选池中的文档重新评分；相关文档没有进入候选池时，它没有机会评分，因此需要先改善召回，而不是单纯加强重排。

**原文依据：** “融合负责从两路结果中产生统一的候选池，重排序负责在这个候选池上精排。”见[第三章·混合检索](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L426)，两类检索的盲区见[第 415 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L415)。

### 30.7 Recall@k 与 Hit@k 有什么区别？

**参考答案：** 对单个查询，Recall@k 是“前 k 项中的相关文档数 ÷ 全部标注相关文档数”；Hit@k 表示前 k 项是否至少命中一篇相关文档，命中记 1，否则记 0，再对查询集求平均得到命中率。若共 4 篇相关文档、前 5 项找到 2 篇，则 Recall@5 为 0.5，Hit@5 为 1。每题只有一篇相关文档时，两者对任意检索结果都相同；有多篇时则可能不同。

**原文依据：** 「严格说，本书这里定义的“recall@k”实为命中率」。见[第三章·表 3-3 的 recall 脚注](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L444)。本题采用脚注中的严格定义，不直接沿用表中的简化称呼。

### 30.8 为什么 Top-k 片段不能用于统计整个数据集的总体规律？

**参考答案：** Top-k 按相关性挑选少量记录，既不是完整数据，也通常不是随机样本。以这些结果计算比例，会同时受到数量截断和相关性选择偏差影响。总体统计应明确范围、枚举或查询完整记录，由 SQL/代码聚合；也可以检索预先计算且来源完整的统计结果，并核对统计口径与版本。

**原文依据：** 「统计类问题需要“数遍所有文档”，而检索的本性是“找最相关的几个”」。见[第三章·黑猫白猫的计数问题](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L468)。完整数据聚合是从该案例得到的工程解法。

### 30.9 RAPTOR、GraphRAG 与文件层级分别补充了什么结构？

**参考答案：** RAPTOR 用递归聚类和摘要形成从细节到概览的层次；GraphRAG 用实体、关系及社区组织知识，支持关系关联与多跳查询；文件层级用目录、URI、概览和全文组织可浏览的知识空间。它们分别强化抽象层次、关系网络和导航结构，可结合使用。实体是否正确、摘要是否忠实仍需核验。

**原文依据：** “这种树状结构使得检索可以在多个抽象层次上进行”。见[RAPTOR](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L484)。另见[GraphRAG 的实体关系结构](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L490)与[文件系统的 L0/L1/L2](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L527)。

### 30.10 修改原文后，哪些派生索引与摘要也需要更新？

**参考答案：** 需要追踪受影响的分块、背景前缀、向量、倒排索引、层级摘要、实体关系和引用元数据。内容删除或权限变化时，还要使旧结果失效，防止继续检索到旧知识。合理流程是先审核知识变更，再从确定版本重建受影响的派生物，最后通过代表性查询验证新旧状态。

**原文依据：** “增量重建受影响的分块、摘要和向量索引。”见[第三章·增量更新的发布步骤](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L546)。原始证据、知识和服务三层见[第 548 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L548)。倒排、图关系等属于结合本章各类索引补充的依赖检查范围。

### 30.11 Agentic RAG 与第一章的 ReAct 循环有什么共同点？

**参考答案：** 两者都让模型依据当前证据决定行动，工具返回观察后更新上下文，再决定继续还是回答。Agentic RAG 把知识库搜索和文档读取工具化，模型可以拆解问题、改写查询、补查与交叉验证。变化主要是工具和知识来源，第一章的决策—行动—观察框架仍然适用。

**原文依据：** 「Agent 采用 ReAct 模式（参见第一章定义），通过“思考→行动→观察”的循环主导整个过程。」见[第三章·智能体化 RAG](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L578)。

### 30.12 Contextual Retrieval 在哪个阶段起作用，与回答时摘要有何区别？

**参考答案：** Contextual Retrieval 在建索引时为片段补充背景，例如主体、文档主题和时间，再把前缀与原片段一起索引，解决片段脱离全文后难以理解和检索的问题。回答时摘要或上下文压缩发生在运行阶段，面向当前问题筛选与缩短已有材料。一个提高入库片段的可检索性，一个管理当前上下文预算。

**原文依据：** “一个在做加法（补上下文），一个在做减法（去冗余）。”见[第三章·上下文感知检索与压缩的区分](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L636)。前缀生成过程见[第 634 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L634)。

### 30.13 为什么概览卡片与历史检索可以共同改善主动关联？

**参考答案：** 少量概览卡片让模型知道用户有哪些重要背景，因此更容易发现新任务与旧信息的关联；历史检索再提供日期、条件和变化过程等细节。只有检索时，模型可能没想到应搜什么；只有概览时，又可能缺少准确细节。双层结构分别支持“想到相关信息”和“核实相关信息”。

**原文依据：** 「它要求系统同时握有“全局概览”和“精确细节”两种视角」。见[第三章·双层记忆架构](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L667)。

### 30.14 为什么因子重要性不等于因果关系，向量也不等于一个聊天 token？

**参考答案：** 因子重要性说明某个特征在当前统计方法中有区分或预测价值；它可能受其他变量、样本选择和编码方式影响，不能直接解释为“改变该特征就会导致结果改变”。本地原型实现按聚类中心与权重计算区分性分数，没有在这里建立因果识别设计。

Embedding 是一组数值表示，聊天 token 则是接口处理序列的单位。把向量数字写成 JSON 会被当作文本分词；要让一个向量作为模型内部的一个位置参与计算，需要专门的输入机制与训练支持。

**原文依据：** 「通过分析定义聚类的关键特征，构建数据驱动的“因子重要性层次模型”。」见[第三章·实验 3-12](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L691)。向量进入上下文的设想见[多模态记忆·思路二](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter3.md#L703)。

**补充判断：** 原文没有直接论证“相关不等于因果”，并把“一嵌入占一个 token”写在前沿设想中；本题补充的是方法和接口边界，不将其当作通用 API 已实现的事实。可核对[本地因子评分计算](https://github.com/bojieli/ai-agent-book/blob/main/chapter3/structured-knowledge-extraction/archetypes.py#L159)。
