# Chapter 4 知识点总结：工具设计与事件驱动的异步 Agent

> 依据：[第四章正文](../book/chapter4.md)、[配套项目目录](README.md)、[实验台账](EXPERIMENT_LEDGER.md)，并结合 MCP 接入、执行工具、协作工具、异步运行时及工具发现代码整理。整理日期：2026-09-15。实验状态引用仓库既有记录，本次未运行外部 API、发送消息或修改业务代码。

## 1. 本章主线：让 Agent 的行动可用、可控、可持续

前四章可以连起来理解：

- 第一章：模型怎样通过 ReAct 循环决定下一步。
- 第二章：每一步应该向模型提供什么上下文。
- 第三章：跨会话记忆与外部知识怎样存储、更新和检索。
- 第四章：怎样设计工具接口，以及怎样处理工具执行期间不断到来的事件。

第四章有三条相互连接的主线：

```text
设计能力：工具做什么、参数怎样传、结果怎样返回
管理执行：权限、审批、验证、超时、重试与取消
组织运行：协作、事件队列、异步任务与按需发现工具
```

从第一章的网页搜索例子继续往下看：模型生成 `tool_calls` 之后，Harness 还要决定调用哪个真实服务、是否允许执行、怎样返回结果，以及执行没结束时如何响应用户。

## 2. 五类工具与各自的设计重点

| 类型 | 交互方向 | 主要用途 | 设计重点 |
|---|---|---|---|
| 感知工具 | Agent 主动调用 | 搜索、读取、理解外部信息 | 输出范围、分页、来源与时效 |
| 执行工具 | Agent 主动调用 | 写文件、执行程序、修改外部系统 | 权限、副作用、验证与恢复 |
| 协作工具 | Agent 主动调用 | 委托子 Agent、请求人类协助 | 任务边界、上下文交接与生命周期 |
| 事件触发工具 | 注册后由外部触发 | 定时唤醒、监控任务、接收回调 | 触发条件、过滤、去重与调度 |
| 用户沟通工具 | Agent 主动调用 | 回复、通知、发送卡片或附件 | 渠道、收件人、时机与送达状态 |

这是按功能理解工具的分类，不是严格互斥的服务器目录结构。例如，`perception-tools` 也打包了移动、复制、删除文件的能力；这些操作依然有副作用，要按执行工具管理。

同一个 `send_email`，用于联系业务方时是执行动作，用于告知用户进展时承担沟通功能。判断风险应看实际操作，而不是目录名字。

## 3. 专用工具，还是 Skill + 通用执行器

Agent 能力有两种常见表达形式：

- **专用工具**：把一个能力封装成有明确参数和返回值的接口。
- **Skill + 通用执行器**：用文档描述流程，通过终端、代码解释器等通用工具执行。

| 判断维度 | 更适合专用工具 | 更适合 Skill + 通用执行器 |
|---|---|---|
| 参数复杂度 | 嵌套对象、联合约束、严格字段校验 | 参数简单、已有清晰 CLI |
| 变更频率 | 稳定的底层能力与业务契约 | 经常调整的流程、知识和操作顺序 |
| 模型能力 | 希望减少自由编排和转义负担 | 模型擅长读文档、编程与排错 |
| 安全边界 | 需要精细授权、审计或限制写操作 | 执行范围可通过通用环境有效约束 |

例如，“分析 CSV 并生成图表”可由 Skill 指导代码解释器完成；“修改生产订单状态”更适合有业务校验的专用接口。

Skill 中的脚本、命令和流程同样需要测试。能力以文档表达，只改变组织方式，不会自动获得账号、网络或文件权限。

## 4. 工具粒度：何时合并，何时拆开

合并的判断依据是：目标相近、参数类似、输出形式相近、使用场景重叠。

例如，读取多种文档格式可以统一为 `read_document(path, ...)`，由内部实现分派。模型只需理解一个目标，新增格式也较容易。

适合拆开的情况包括：

- 参数集差异很大，例如 OCR 与视频关键帧分析。
- 权限或副作用不同，例如读取订单与取消订单。
- 延迟与费用差异大，需要模型明确选择。
- 某项高频能力需要简洁、稳定的专门接口。

工具太细会增加选择和串联成本，工具太粗会形成参数复杂、边界模糊的“大一统接口”。工具数量与 schema 长度应在实际任务上评估，不存在统一的“超过多少个就必然失效”阈值。

## 5. ACI：从 Agent 的任务出发设计接口

ACI（Agent-Computer Interface）关注 Agent 如何理解和操作计算机。

与“每个底层 API 端点包装一个函数”相比，面向任务的工具要让模型容易判断：

1. 当前目标应该用哪个工具？
2. 需要哪些参数，怎样得到这些参数？
3. 会产生哪些影响？
4. 返回结果能支持什么下一步决策？

通用执行器能覆盖计算、转换和批处理等大量任务；专用接口可以把复杂权限、跨平台差异或业务规则封装起来。两者通常组合使用。

## 6. 一份好工具说明应包含什么

| 内容 | 应回答的问题 |
|---|---|
| 使用条件 | 什么时候应该调用？ |
| 功能边界 | 能处理哪些对象，哪些情况应换工具？ |
| 参数约定 | 类型、单位、范围、枚举、格式与例子是什么？ |
| 返回契约 | 返回哪些字段，空结果和失败如何表达？ |
| 执行代价 | 是否耗时、计费、有速率限制或副作用？ |
| 调用示例 | 常见任务如何组合参数？ |

例如，`timestamp` 应说明时区和单位；文件搜索应说明匹配的是文件名还是正文。遇到工具选择错误，先检查描述、候选重叠和上下文，再分析模型能力。

JSON Schema 可描述类型、范围、枚举和部分组合约束；示例补充典型用法和隐含约定；运行时验证负责检查真实参数。三者各有作用。

下面是 **MCP 工具定义的简化示意**，不是本地某个工具的原样 schema：

```json
{
  "name": "read_document",
  "description": "读取已知路径的文档；搜索未知文件位置时请先使用文件搜索工具。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "path": {"type": "string", "description": "授权目录内的文档路径"}
    },
    "required": ["path"]
  }
}
```

客户端会按模型接口要求适配这些元数据。MCP 的 `inputSchema` 与某个模型 API 的 `function.parameters` 属于不同层的表示。

## 7. 参数保真性：读到什么，就能准确操作什么

工具传递参数时应保留调用者的实际意图。两个典型错误是：

- **静默转换**：把中文弯引号变为直引号，导致精确替换无法匹配原文件。
- **静默注入**：私自给命令增加选项，导致执行行为或兼容性发生变化。

如果确实需要编码、路径或格式规范化，应明确约定并报告实际使用的值。日志也应能关联原始参数与执行参数，以定位“模型看见的内容”和“工具实际操作的内容”之间的偏差。

对精确编辑工具，还应处理零匹配、多处匹配、文件已变更等状态，避免把模糊匹配当作确定修改。

## 8. 工具调用、工具发现与代码编排

书中用三个阶段概括工具设计的发展，可以理解为三个叠加的关注层次：

1. API 封装：把外部能力变成可调用接口。
2. ACI 设计：按任务目标调整粒度、说明和反馈。
3. 调用与组织优化：用示例减少误用、按需发现工具、用代码编排重复操作。

代码编排适合依赖关系已明确的批处理：模型生成一段受控程序，程序内部读取多个结果、转换并汇总，最后只把必要结论和产物引用返回上下文。

它减少中间数据反复进入模型的成本，但每个高风险调用仍须经过授权和验证。是否交给代码，取决于中间步骤是否需要新的开放式判断。

## 9. MCP：统一能力接入，不替代 Agent 运行时

MCP（Model Context Protocol）为客户端与工具、数据服务提供标准化交互方式。

```text
用户任务
   ↓
Agent / Host：组织上下文、调用模型、决定执行策略
   ↓ 内部 MCP Client
MCP Server：暴露工具、资源或模板
   ↓
文件、数据库、业务 API、计算环境
```

这里的“Server”既可以是本机进程，也可以是远程服务，不必是一台独立机器。

三类基本能力：

- **Tools**：可执行操作，包括读取型与写入型操作。
- **Resources**：可由应用读取的上下文数据，如文件和记录。
- **Prompts**：可选用的提示模板。

本章介绍了本地 stdio 和远程 HTTP 等传输方式。具体协议版本、鉴权和客户端兼容性应在接入时核对；本总结侧重架构关系。

MCP 负责能力交互，事件接入、任务调度、跨会话状态和常驻服务由外层运行时负责。后端采用 MCP，与前端是否一次性加载全部工具 schema，是两个独立选择。

## 10. 代码中一次 MCP 工具调用怎样完成

阅读 [agent-with-event-trigger/agent.py](agent-with-event-trigger/agent.py) 的 `MCPServerManager`，可以看到：

```text
配置工具服务器
  → 建立 stdio 连接并 initialize
  → list_tools 获取工具声明
  → 保存服务器与工具的对应关系
  → 将声明提供给 Agent
  → 模型选择工具并生成参数
  → call_tool 路由到对应 MCP Server
  → 返回结果，继续 Agent 循环
```

本地这份实现为工具名添加服务器前缀，并在实际调用时建立新的服务器连接。它说明了“发现元数据”和“执行工具”是两步；长期运行系统还要根据有状态会话、启动开销和生命周期要求选择连接管理方式。

与第一章 Kimi Formula 相比，变化的是工具接入和调用协议；“模型决策 → 程序调用真实工具 → 结果回到上下文”的骨架保持一致。

## 11. MCP 的信任边界

接入一个服务器，也引入了工具描述、执行代码、返回数据和凭证使用的信任边界。

| 风险 | 表现 | 防护重点 |
|---|---|---|
| 描述投毒 | 工具说明夹带窃取信息或绕过规则的指令 | 审查描述，按不可信输入处理 |
| 供应链变化 | 更新或服务器被入侵后行为改变 | 版本与来源追踪、变更审查 |
| 工具遮蔽 | 同名或近似工具诱导错误路由 | 服务器身份、命名空间与明确路由 |
| 凭证滥用 | 高权限令牌被用于非预期操作 | 最小权限、有效期、隔离与撤销 |

尤其要检查“私有数据访问 + 不可信内容 + 对外通信”同时存在时的泄露路径。权限应在执行层强制实施，工具说明、来源标签和模型审查提供辅助判断。

## 12. 感知工具：返回足够的信息，并说明覆盖范围

### 搜索与读取分开

- 搜索返回标题、位置、摘要等候选信息。
- 模型选择相关候选，再读取原文。
- 结果很多时提供分页或 cursor，让模型决定是否继续。

### 大文件按范围读取

读取工具提供行号、页码或 offset/limit 等范围参数。截断应说明已经展示的范围、剩余部分及继续读取方法。

例如：“显示第 1—200 行，共 5,000 行，可从第 201 行继续读取。”这种返回能够帮助模型判断证据是否完整。

### 摘要与原文分层

长输出可按任务目标压缩，但应保留原文引用或存储位置。需要精确字段、完整条件或审计时，模型仍可回到原始资料。

只读调用通常适合并发与缓存；缓存必须考虑查询参数、身份权限、数据版本和有效期，并发也要遵守速率限制与一致性要求。

## 13. 多模态感知的三种方案

| 方案 | 处理方式 | 适用情况 | 主要代价 |
|---|---|---|---|
| 原生多模态 | 主模型直接接收图像等内容 | 需要综合理解图文、布局与空间关系 | 输入与处理成本取决于模型和分辨率 |
| 提取为文本 | OCR、转录或文档解析后输入文本 | 文字主导的材料 | 可能丢失图表、布局、语气等信息 |
| 工具化分析 | 主模型向多模态工具提出具体问题 | 按需检查局部视觉或音频内容 | 工具回答可能压缩或遗漏细节，需要追问 |

例如，读取一页纯文字报告可优先文本解析；理解流程图中的箭头关系需要视觉信息；纯文本主模型也可以调用视觉工具分析指定图片。

比较方案时记录整体费用、延迟、信息保真度和答案质量，而不仅看主模型输入长度。原生模型、提取器、工具内部模型的能力都会影响结果。

代码入口：[multimodal-agent/agent.py](multimodal-agent/agent.py)，重点看 `process_multimodal_content()`、`_process_native()`、`_extract_to_text()` 和 `MultimodalTools`。

## 14. 执行工具的分层安全体系

执行工具直接改变文件、进程或外部业务状态，需要多层控制：

1. **输入验证**：检查类型、路径范围、参数格式及命令注入风险。
2. **权限控制**：限制工作目录、账号权限、网络访问与可执行能力。
3. **风险审批**：对需要确认的动作，在执行前完成批准。
4. **隔离与预算**：限制运行环境、CPU、内存、磁盘、进程数、网络与时长。
5. **结果验证**：检查实际状态和产物是否满足要求。
6. **审计与恢复**：记录调用、处理失败、控制重试，必要时回滚或转人工。

路径校验应基于解析后的真实路径，而不只是检查字符串前缀。危险命令黑名单只能覆盖已知模式，不能代替操作系统权限与隔离机制。

## 15. 提议者—审核者：事前审批与事后验证

两种机制解决不同问题：

- **事前审批**：判断计划和具体操作是否符合授权与规则。
- **事后验证**：判断执行结果是否达到目标。

审核可以采用独立模型、人类或确定性检查。两个模型应获得一致的可信规则与必要事实，分别侧重行动与验证；采用不同模型可以增加视角差异，但实际审查效果仍需测量。

拒绝应返回明确原因，供 Agent 修改方案。连续被拒绝时停止循环或升级处理，而不是换个说法反复申请。

事后验证可切换观察方式：代码生成文档后检查渲染效果，修改配置后通过测试环境验证行为。验证应选择能观察真实结果、成本与风险合适的手段。

## 16. Sidecar：旁路检查与单次调用门控

Sidecar 是伴随主流程运行的辅助模块。在安全场景中，它读取工具名、具体参数、可信授权范围等必要信息，判断本次调用是否可以放行。

```text
主模型生成工具调用 ─────→ 继续生成后续内容
          ↓
     旁路风险检查
          ↓ 批准后
       执行该工具
```

审查可以与主模型的其他工作重叠，但被审查的危险操作必须等放行后再执行。进度提示可以写“正在检查操作权限”，不能把尚未放行描述成已经成功执行。

与广义提议者—审核者相比，安全 Sidecar 通常聚焦单次调用，输入更窄、目标更明确。两者是可组合的设计方式。

结构化输入减少无关话术干扰，但 JSON 字段里的命令或文本仍可能包含攻击内容；需要与确定性规则、权限校验和隔离结合。

Sidecar 还可以旁路筛选记忆、生成摘要或准备上下文。这些用途可以共享“辅助计算与主流程重叠”的思路，权限和输入范围则按任务分别设计。

## 17. 执行—验证—反馈闭环

工具返回应帮助模型判断下一步，而不只是一个笼统的 `success`：

```text
写入或运行 → 编译 / 检查 / 测试 / 读取实际状态
                           ↓
                 结构化返回结果与错误
                           ↓
                 Agent 修正或继续下一步
```

例如，Python 编译检查可发现语法错误，静态分析可发现部分未定义名称，测试验证具体行为。它们检查的层次不同，语法通过不等于业务正确。

本地 [file_tools.py](execution-tools/file_tools.py) 的 `write_file()` 会先检查路径与覆盖策略，并在写入前调用代码语法验证；这与正文“写入后验证”的描述在时机上不同，但都体现了验证与工具执行结合的思路。

## 18. 长输出、日志与产物引用

长命令输出可以采用：

- 上下文保留头尾预览与关键错误。
- 明确说明截断范围。
- 完整输出保存到受控路径，返回路径或产物 ID。
- 按需搜索、读取完整结果。

工具日志记录调用 ID、时间、目标、参数、结果、耗时和状态，并对敏感字段做最小化记录或脱敏。

返回文件路径只节省信息传递成本。使用者仍需具有读取权限；远程客户端也需要下载、资源读取或其他可访问机制，不能假设都能打开同一个本机路径。

## 19. 虚拟环境、容器与虚拟机

| 机制 | 主要解决什么 | 安全边界 |
|---|---|---|
| Python venv | 项目依赖与解释器环境隔离 | 不限制文件、网络或进程权限 |
| 本地受限进程 | 在用户/进程权限及系统策略下运行 | 取决于实际账号、沙盒与权限配置 |
| 容器 | 文件系统、进程、网络等隔离 | 通常共享宿主内核，挂载与配置影响风险 |
| VM / microVM | 独立内核及更强的运行隔离 | 仍需管理共享目录、凭证、网络与资源 |

前面讨论的项目虚拟环境解决的是依赖管理问题；运行不可信命令还需要另外的安全控制。

隔离环境中的程序依然可能通过授权账号修改真实业务数据，所以环境隔离和外部系统授权必须同时设计。

## 20. 幂等性、超时与取消语义

最重要的区分是：

```text
请求超时 ≠ 服务端未执行
取消本地等待 ≠ 取消远端任务
任务已取消 ≠ 已发生的副作用被撤销
```

**幂等性**：重复提交同一个逻辑操作，对外部状态的影响与提交一次相同。

常见实现包括服务端幂等键、唯一业务约束、操作记录与状态查询。重试应复用同一逻辑操作 ID；单纯“先查有没有，再创建”在并发下可能竞争，还需要服务端去重或原子约束。

发送邮件、付款等动作会产生真实事件，也可以由支持的服务端机制提供重复请求去重。对于缺乏可靠去重的接口，应采用预检、预览和确认，并在结果不明时先核查状态，避免盲目重发。

确认令牌应绑定具体操作、参数和有效期。预检能减少误操作，但不能独自消除执行后的网络不确定性。

## 21. 协作工具与子 Agent 生命周期

子 Agent 的价值是专业化、并发与上下文隔离。每个子任务应明确：

- 目标与职责边界。
- 可用工具和权限。
- 来自主 Agent、用户和工具的数据来源。
- 输出格式、证据要求与完成条件。
- 遇到缺失信息时如何上报。

生命周期原语可以概括为：创建、发送消息、查询状态、取消，以及发现可用协作者。

| 协作形式 | 行为 | 适合情况 |
|---|---|---|
| 同步 | 等待子任务结果 | 短任务、下一步依赖结果 |
| 异步 | 立即返回任务 ID，稍后取回结果 | 长任务、独立并发任务 |
| 流式 | 持续汇报增量结果 | 中间进展有使用价值 |
| 多轮 | 子任务追问，主任务补充 | 需求需要逐步澄清 |

上下文交接可选择最小任务参数，或由模型从主轨迹提炼交接摘要。前者简洁但可能缺背景，后者更完整但有生成成本和遗漏风险。

代码入口：[subagent_tools.py](collaboration-tools/src/subagent_tools.py)。重点看 `spawn_subagent()`、`send_message_to_subagent()`、`cancel_subagent()`、`get_subagent_status()` 以及两种上下文准备函数。

## 22. HITL：把人工确认设计成有状态的流程

Human-in-the-Loop 适用于缺失授权、关键偏好、重要业务判断与高影响操作。

一个完整请求需要包含：请求 ID、具体待确认事项、参数或预览、响应期限、默认行为和当前状态。

```text
pending → approved / rejected / timeout / cancelled
```

超时采用预先规定的保守行为；已经进入终态的请求应拒绝重复或迟到响应，防止过期批准被重新用于执行。

本地 [hitl_tools.py](collaboration-tools/src/hitl_tools.py) 的 `respond_to_request()` 会检查请求是否仍为 `pending`。台账保留了过去一次迟到响应暴露问题的记录，以及随后加入的保护。

人类批准、拒绝及理由可以形成后续评估与知识更新的材料，经过审核后再进入规则、Skill 或训练数据。

## 23. 事件触发与用户沟通

事件触发分为两个时刻：注册关注条件，以及事件到来后唤醒处理。

- **定时器**：一次性或周期性唤醒，需要明确时间和时区。
- **后台监控**：订阅任务进度、关键输出、退出或超时事件。
- **外部通道**：接收邮件、消息、Webhook 或其他系统回调。

推送能及时响应变化；不支持推送的服务仍可由定时检查转换成事件。事件驱动与轮询可以组合，重点是避免让模型反复调用查询工具做无效等待。

书中的 Hooks、Cron、Heartbeat 与 Channel 案例用于区分生命周期事件、时间驱动和外部推送。具体产品支持范围随版本变化，理解机制时不必把案例中的某项限制当成永久边界。

沟通工具则让 Agent 主动选择收件人、渠道、内容、附件和通知强度。需要分别记录“已提交发送”“已送达”“已读”“已回复”，并控制重复通知和跨渠道信息泄露。

## 24. 独立身份与共享执行环境

Agent 可以使用专属账号代表用户行动，也可以在明确授权下使用用户账号。选择依据包括业务需要、账号能力、可审计性与风险范围。

- 专属身份便于隔离和撤销权限，并应明确其代理角色。
- 需要用户登录时，由用户通过可信认证流程完成，不把密码或验证码随意写入轨迹。
- 虚拟电脑或手机为操作提供独立环境；共享目录用于交换获授权的输入和产物。

共享挂载应限于必要范围，避免把宿主机全部文件暴露给 Agent。服务访问受阻时，应采用官方接口、允许的自动化方式或用户协助。

## 25. 异步、并发与事件循环

同步调用通常等待结果后再继续；异步调用允许等待期间调度其他工作。**异步不等于多线程，也不等于 CPU 计算在同一时刻并行。**

在 Python 中可以这样理解：

- `async def` 定义协程函数。
- `await` 等待异步结果，并在需要等待时让出调度机会。
- `asyncio.create_task()` 安排协程并发推进。
- `asyncio.Queue` 传递事件，`gather()` 等待多个任务。
- `task.cancel()` 请求取消；清理子进程和处理外部副作用仍需显式逻辑。

阻塞式网络调用或 CPU 密集计算直接放入协程，仍可能堵住事件循环。端点写成 `async def`，不自动使内部全部操作非阻塞。

## 26. 事件模型：来源、关联与真实状态

事件应包含足够的信息供运行时路由、去重和关联。以下是结合正文补充的工程示意，非项目固定 schema：

```json
{
  "event_id": "evt_102",
  "type": "task.completed",
  "source": "task_runner",
  "session_id": "session_7",
  "task_id": "task_9",
  "occurred_at": "2026-09-15T10:00:00+08:00",
  "payload": {"status": "succeeded", "artifact_id": "report_9"}
}
```

运行时事件记录与模型 `messages` 是两种表示：前者承载真实状态、路由与审计，后者是本次模型输入。不是每个日志字段都需要发给模型，也不能把第三方事件一律当成用户授权。

生产实现还应验证来源、限制载荷、按事件 ID 去重、处理重复或乱序回调，并管理积压与背压。这些控制由程序维护，模型辅助理解语义。

## 27. 三种事件处理策略与安全点

| 策略 | 处理方式 | 示例 |
|---|---|---|
| 取消式 | 请求停止当前工作，确认状态后处理新事件 | 用户说“停止，目标文件选错了” |
| 队列式 | 暂存事件，到安全边界批量处理 | 用户补充“用日语，整理成网页” |
| 并行式 | 为独立任务提供另外的处理路径 | 长分析期间回答时间查询 |

**安全点**是运行时能一致地更新轨迹和状态的边界，例如一轮模型输出完成、工具结果到达或取消清理完成。外部事件先进入队列，再由运行时决定何时纳入模型输入。

取消式处理可以主动请求中止，提前到达边界；它仍需遵守工具的取消语义。并行任务还要检查共享文件、账号和业务状态的冲突。

明确的停止按钮可直接按规则路由，语义模糊的自然语言可交给分类模型辅助判断。外部消息不能仅因自称“紧急”就取得更高权限。

## 28. 工具没完成时，`messages` 怎样变化

第一章的常规链路是：`assistant(tool_calls) → tool(result) → 下一次模型调用`。

对于要求调用与结果配对的接口，长任务可采用**启动回执 + 稍后完成事件**：

```text
user：启动分析
assistant：调用 start_analysis
tool：已启动，task_id=T1，status=running
assistant：任务正在后台运行

user：现在几点？
assistant/tool：查询并回答时间

后续事件：T1 已完成，附真实结果
assistant：读取结果并给出分析结论
```

启动工具已经完成“提交后台任务”这一职责，所以立即返回任务 ID 是真实结果。分析任务是否完成，则由任务管理器的后续事件说明。

书中还讨论了在打断时为尚未完成的同步工具补充状态占位符。使用时要清楚标记 `running`、`cancelled` 或未知状态，按实际 API 保持调用 ID 配对；后续真实结果作为带任务关联的新事件处理，避免给同一调用重复追加非法结果。

应始终区分：模型请求已取消、工具任务已停止、远端操作状态未知。未完成的模型流也不能当作完整消息随意写入历史。

## 29. 批量事件、恢复与检查点

批量处理时，应把事件编号、来源、任务关联和未解决事项显式呈现，并维护程序侧的处理状态。第二章的状态栏在这里用于提醒待办，减少只回应最后一条事件的遗漏。

长期运行需要保存：轨迹、任务 ID、已知进度、结果引用、队列与必要配置。恢复时先核查实际任务状态，再决定重连、重跑或等待。

本地 [tasks.py](async-agent/tasks.py) 的 `restore()` 将保存时为 `running` 的任务恢复为 `suspended`。这是恢复任务记录，不是自动复活原来的操作系统进程，也不是恢复模型脑中的推理。

## 31. 主动工具发现：把能力缺口变成检索请求

| 策略 | 何时确定工具集 | 主要取舍 |
|---|---|---|
| 全量注入 | 会话开始提供全部定义 | 覆盖直接，但上下文较大 |
| 一次预筛选 | 按最初问题选一组候选 | 开销较低，可能遗漏后续需求 |
| 主动发现 | 执行中根据能力缺口按需搜索 | 适合跨领域任务，增加发现步骤 |

主动发现的循环：

```text
发现缺少能力 → discover_tools(need)
      → 检索候选工具 → 加载定义 → 校验权限并调用
      → 根据结果继续执行或发现新工具
```

规模较大时可先匹配服务器，再匹配具体工具。索引可以使用语义嵌入，也可以结合关键词、类别与规则。低相关候选应返回未找到，帮助模型改写需求或选择已有替代方案。

### 与 KV Cache 的关系

在支持的协议中，新定义只在发现时追加，后续保持原位置，使之前的稳定前缀具备复用条件。缓存实际命中还取决于模型、有效 token 前缀、服务端缓存策略和保留时间。

加载一段 schema 文本与注册可执行能力是两步：运行时必须提供分派器和权限控制。不能把 schema 粘到普通消息中，就假定任意模型 API 会自动支持该工具。

### 本地代码与实验协议

[active-tool-discovery/agent.py](active-tool-discovery/agent.py) 比较三种策略，使用模型生成 JSON 文本、程序解析并分派的 ReAct 协议；[discovery.py](active-tool-discovery/discovery.py) 提供索引与搜索。正式实验入口是 [run_exact_experiment.py](active-tool-discovery/run_exact_experiment.py)，使用真实 MCP 工具目录和调用。

[active-tool-selection](active-tool-selection/README.md) 是补充项目，其中 [semantic_router.py](active-tool-selection/semantic_router.py) 展示服务器与工具两层匹配。不要把离线演示的模拟后端与正式实验结果混用。

## 32. Skills 视角与研究方向

Skills 将能力组织成目录、流程、脚本和参考资料，Agent 按当前任务逐步读取。相比维护大量专用函数，这种方式适合复用已有 CLI 与可编排流程。

复杂参数仍适合用结构化对象、文件或专用接口传递，减少 Shell 引号与转义错误。Skill 的元数据、引用路径和脚本有格式及执行要求，修改后仍需验证。

本章还讨论了持续思考、异步训练和可组合 KV Cache 等研究方向：希望模型更好地理解延迟结果、恢复打断与批量事件，并降低重复加载知识的成本。这些属于原文的前沿讨论；通用聊天接口不能仅靠拼接思考标签就可靠实现它们，也不能任意移动普通 KV 缓存块而保持语义等价。

本轮总结采用的工程基础仍是明确的工具协议、任务状态机、事件调度和可验证的结果。

### 35.1 五类工具分别由谁发起，为什么事件注册与触发是两个时刻？

**参考答案：** 感知、执行、协作和用户沟通由 Agent 主动调用。事件触发工具则先注册关注条件，再由定时器、后台任务或外部系统在条件满足时发送事件。比如“明早提醒”是在现在注册定时器，明早才触发唤醒。区分两步，才能理解 Agent 如何在本轮回复结束后继续被事件驱动。

**原文依据：** “注册时由 Agent 主动调用工具，声明自己关心什么事件”。见[第四章·事件触发工具的分类说明](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L30)及[五类工具表](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L13)。

### 35.2 哪些能力适合专用工具，哪些适合 Skill + 通用执行器？

**参考答案：** 参数复杂、需要严格业务校验或精细权限的能力适合专用工具；已有清晰 CLI、参数简单、流程经常变化的能力适合 Skill 指导通用执行器。还要考虑模型是否擅长编程、命令转义和排错。稳定底层接口与可变流程可以组合，Skill 的执行权限依然由环境和业务系统控制。

**原文依据：** “涉及嵌套对象、多字段联合校验、复杂类型约束的操作”。见[第四章·参数复杂度](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L47)，其余两个判断维度见[变更频率](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L48)和[模型能力](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L49)。

### 35.3 怎样判断两个工具应该合并还是拆开？

**参考答案：** 目标、参数、输出和使用场景相近时可以合并，例如统一读取多种文档格式；参数形态、执行成本或权限差异很大时适合拆开，例如读文件与删除文件。合并减少选择负担，拆开保持语义和安全边界清晰。应围绕模型完成任务时的实际使用方式决定粒度。

**原文依据：** “判断是否应该整合的核心标准是功能相似性和使用场景的重叠度。”见[第四章·工具粒度](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L55)，保持独立的条件见[第 57 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L57)。

### 35.4 工具描述、schema、示例与运行时校验各承担什么作用？

**参考答案：** 描述说明何时使用、用途与边界；schema 表达类型、必填字段、枚举和可表达的约束；示例展示典型参数组合、单位和调用方式；运行时校验检查本次真实参数是否符合契约、资源范围和权限。模型理解正确与参数实际合法是两道检查，不能只依靠说明文字。

**原文依据：** 「发现异常输入时立即拒绝，不尝试“智能”修正。」见[第四章·输入验证](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L215)。说明和示例见[工具描述的艺术](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L67)。

### 35.5 为什么参数静默转换会导致 Agent 反复失败？

**参考答案：** 模型依据读取结果构造参数，工具却在传递时偷偷改变参数，就会形成难以从当前观察中发现的偏差。例如读到中文弯引号后按原样请求替换，执行层却改成直引号，精确匹配便反复失败。解决方法是保持参数保真，必要的规范化要事先声明，并返回实际执行值或明确错误。

**原文依据：** “模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差”。见[第四章·参数传递的保真性](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L93)。

### 35.6 MCP Server、MCP Client、模型与 Agent 运行时分别做什么？

**参考答案：** Server 暴露工具、资源和模板并处理请求；Client 负责连接、发现与协议调用；模型根据上下文选择能力、生成参数和后续响应；Agent 运行时组织模型输入、实施授权、调度工具、维护消息与事件。模型调用协议与 MCP 通常由运行时适配，Server 也可以只是本机进程。

**原文依据：** “MCP 服务器暴露一组工具，MCP 客户端（通常是 Agent 框架或 IDE）通过标准化协议与服务器通信。”见[第四章·MCP 架构](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L107)。事件运行时的分层职责见[MCP 的局限性](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L119)。

### 35.7 感知工具为什么需要分页、明确截断与来源信息？

**参考答案：** 分页让模型先看候选，再决定是否扩大检索；明确截断让模型知道只看到了部分内容；来源位置让它能够读取原文、核查事实和引用证据。三者一起控制上下文大小并说明证据覆盖范围，避免把前几条结果误当成全集，或基于不完整文件作出确定判断。

**原文依据：** “让 Agent 先浏览候选，再决定深入读取哪一条。”见[第四章·搜索返回与分页](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L156)，截断与续读方法见[第 158 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L158)。

### 35.8 三种多模态处理方式如何按任务取舍？

**参考答案：** 文字主导的文档可先提取文本；需要理解布局、图表或图文关系时，适合直接使用多模态模型；主模型不支持该模态或只需局部检查时，可以向专门工具提出问题并读取分析。应比较整体质量、延迟与成本，同时关注提取或工具摘要是否丢失任务所需信息。

**原文依据：** “工具接受一个多模态文件和一个自然语言问题作为参数”。见[第四章·工具化多模态分析](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L196)。另外两条路线见[原生多模态](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L184)和[提取为文本](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L188)。

### 35.9 事前审批、Sidecar 与事后验证如何组合？

**参考答案：** 事前审批先判断计划是否符合授权和业务规则；安全 Sidecar 聚焦具体工具调用，可以与主模型的其他工作并行，但危险调用要等其放行；事后验证检查真实结果是否满足目标。它们覆盖“该不该做、这次能否执行、最终是否做对”三个问题，并与确定性校验、权限和隔离一起工作。

**原文依据：** “危险操作在 Sidecar 放行之前不会真正执行。”见[第四章·Sidecar 门控](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L241)。另见[事前审批](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L223)和[事后验证](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L233)。

### 35.10 为什么 venv 不是执行沙盒，容器也不能代替业务授权？

**参考答案：** venv 隔离包依赖，不改变代码所拥有的文件、网络和进程权限。容器提供系统层隔离，但挂载目录、网络和凭证仍决定它能影响什么。即使宿主文件被隔离，容器内程序持有真实账号令牌时仍可修改外部业务数据，所以还需最小权限、操作授权与审计。

**原文依据：** “它只隔离包依赖，对文件系统、网络和进程没有任何安全约束”。见[第四章·执行环境隔离](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L282)。容器之外的业务授权边界，是结合本章[权限控制](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L217)与[MCP 凭证风险](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L144)作出的工程归纳。

### 35.11 超时后怎样判断可否重试，取消为何不等于回滚？

**参考答案：** 超时只表示调用方未及时收到结果，远端操作可能已完成。应使用操作 ID 查询状态；接口支持幂等键时复用同一键，让服务端去重。结果不明又缺乏去重保障时，应先核查或转人工。取消主要阻止后续执行或等待，已经发出的邮件、写入的数据等副作用，需要单独撤销或补偿。

**原文依据：** “当一次调用被取消或超时时，它的副作用到底发生了没有？”见[第四章·幂等性与取消语义](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L300)，去重与查询方法见[第 302 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L302)。取消与回滚的区分是基于副作用问题的补充说明。

### 35.12 子任务交接应保留什么，人工批准过期后怎样处理？

**参考答案：** 交接应包含目标、职责边界、必要背景、可信规则、输入来源、已做工作、证据位置、输出格式与完成条件。可用最小参数交接，也可生成摘要，但应控制遗漏和敏感信息。人工请求应有 ID、有效期及状态；过期后按预定保守策略处理，迟到或重复批准不能改写终态，应重新发起适用的确认流程。

**原文依据：** “上下文来源要明确标注”。见[第四章·子 Agent 提示词](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L331)，超时策略见[第 347 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L347)。拒绝终态请求的代码补充见[`respond_to_request()` 状态检查](https://github.com/bojieli/ai-agent-book/blob/main/chapter4/collaboration-tools/src/hitl_tools.py#L235)。

### 35.13 异步任务的启动回执和最终结果如何进入消息历史？

**参考答案：** 模型请求启动工具，工具立即返回真实的提交结果，例如任务 ID 和 `running` 状态，并与调用 ID 配对；后台任务完成后，再发送关联该任务的新事件，包含真实结果。启动回执表示“已提交”，不是“分析已经完成”。运行时应按具体模型协议将完成事件转换为输入，避免给原调用追加重复或含混的结果。

**原文依据：** “任务成功发起后立即返回任务 ID”。见[第四章·异步工具接口](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L570)。本地代码分别见[启动工具回执](https://github.com/bojieli/ai-agent-book/blob/main/chapter4/async-agent/runtime.py#L312)和[`_on_task_complete()` 完成事件](https://github.com/bojieli/ai-agent-book/blob/main/chapter4/async-agent/runtime.py#L170)。

### 35.14 队列式、取消式和并行式各适合什么事件？

**参考答案：** 队列式适合补充条件、常规结果等，等安全点批量纳入；取消式适合用户明确停止或需要立即改变方向的事件；并行式适合与主任务独立、需要及时响应的查询。选择时除了紧急程度，还要检查依赖、资源冲突和授权。外部消息自称“紧急”并不能使其获得更高权限。

**原文依据：** “让事件等到下一个自然到达的安全点（队列式）、主动提前制造一个安全点（取消式），还是干脆另起一个循环”。见[第四章·事件处理机制](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L456)，三种策略的具体例子见[第 488 行起](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L488)。

### 35.15 恢复检查点与恢复进程有什么区别？

**参考答案：** 检查点恢复的是保存下来的事件、任务 ID、最后进度和结果引用；进程恢复意味着实际执行能继续推进，需要仍存活的进程、外部作业管理器或明确的断点续算机制。本地 `restore()` 将原来的 `running` 改为 `suspended`，说明只是恢复任务记录。下一步要查询真实状态，再决定重连、等待或安全重跑。

**原文依据：** “支持通过任务 ID 取消或查询进度。”见[第四章·实验 4-6 的任务状态要求](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L629)。

**代码补充：** 正文没有直接展开检查点恢复语义；本题的具体答案来自[`TaskManager.restore()`](https://github.com/bojieli/ai-agent-book/blob/main/chapter4/async-agent/tasks.py#L265)，其中明确进行 `running → suspended` 转换，没有恢复原进程的执行栈。

### 35.16 主动发现为何能补充一次性预筛选，又增加哪些工程成本？

**参考答案：** 一次预筛选只依据初始问题，可能漏掉执行中才出现的新能力需求；主动发现让模型在遇到缺口时再描述需求、检索并加载候选。新增成本包括维护工具目录或索引、选择与消歧、发现调用延迟、权限校验和历史中的 schema 管理。候选找不到时还需有改写查询和降级路径。

**原文依据：** “任务开始时无法预见所有需求。”见[第四章·一次性匹配的局限](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L638)，主动发现与层次化匹配见[第 640 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L640)和[第 648 行](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L648)。

### 35.17 实验通过为什么不等于正文中的预期效果得到证明？

**参考答案：** 实验通过表示规定的流程和验收门槛完成，预期效果是否成立则由实际对照数据回答。实验 4-7 两组都完成 3/3、准确率均为 100%，所以该次运行没有观察到预期的准确率提升；它记录了更低的 schema 暴露和耗时，同时保留无关调用、过早结束等轨迹。应分别报告流程完成、观察结果与结论适用范围。

**原文依据：** “预期观察：准确率和任务完成率显著提升。”见[第四章·实验 4-7 的预期](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter4.md#L675)。

**实验依据：** 台账记录两组均完成 3/3，并明确写明预期提升未观察到，见[第四章实验台账·4-7](https://github.com/bojieli/ai-agent-book/blob/main/chapter4/EXPERIMENT_LEDGER.md#L67)；验收与假设分离的定义见[台账说明](https://github.com/bojieli/ai-agent-book/blob/main/chapter4/EXPERIMENT_LEDGER.md#L3)。
